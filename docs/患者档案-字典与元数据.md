## 1. 背景与目标

### 1.1 业务背景

患者档案分两类：

| 类型 | 说明 | 存储 |
|---|---|---|
| **基础档案** | 现有疾病、家族史、既往史、饮食、运动、睡眠、生活习惯 | 统一 JSON；全租户字段集一致（可租户扩展） |
| **病种档案** | 糖尿病、高血压等 | 每病种独立 JSON 结构 |

后续大量业务数据（随访、干预、标签等）可复用 **元数据表** 存储与检索。

### 1.2 设计目标

1. **Schema 可配置**：字段定义、选项、病种模板走 `sys_dict`，不写死在代码。
2. **全文可读**：档案表存完整 JSON，便于回显、导出、审计。
3. **字段可检索**：每个逻辑字段同步到 `people_metadata_info`。
4. **租户隔离**：档案与元数据均以 `tenant_id + people_id` 为边界，**不按机构拆分**。
5. **可扩展**：新增 dict 字段 → JSON 新 key → metadata 自动同步，无需改表结构。
6. **修订可追溯**：字段级 old → new，通用注解 + AOP，P1 必做。

### 1.3 P1 In Scope

| # | 能力 |
|---|---|
| 1 | 表：`sys_dict`、`people_metadata_info`、`people_basic_archive`（改造）、`people_disease_archive`、`field_revision_*` |
| 2 | 字典种子 + `DictService`（平台 + 租户 merge） |
| 3 | `MetadataSyncService`（COMPOSITE → FLAT） |
| 4 | `@RecordFieldRevision` + Service AOP |
| 5 | B 端：基础档案 / 病种档案 GET·PUT + 修订历史查询 |
| 6 | C 端：lifestyle GET·PATCH（独立接口，服务端 merge） |
| 7 | 病种：高血压仅 **确诊时间**；糖尿病含类型 + 典型/不典型症状 |

### 1.4 P1 Out of Scope

- 病种 **ARCHIVED / 归档** 功能（表结构不预留 status 流转 API）
- 租户 dict 覆盖管理 UI
- C 端编辑家族史 / 既往史 / 现有疾病（仅 B 端接口开放）
- `people_archive_revision` 整段快照表（字段级 revision 已覆盖）

## 2. Grill 决策摘要

### 2.1 架构与归属

| # | 结论 |
|---|---|
| G1 | 档案归属 **租户级**；`org_id` 仅作操作上下文写入 revision / audit |
| G2 | `dict_type` 使用 **VARCHAR(32)**，不用 int |
| G3 | 复合字段 metadata 策略：**FLAT**（如 `basic.diet.appetite` 各一条） |
| G4 | 字段扩展：dict 增 FIELD → JSON + metadata 自动同步 |
| G18 | **metadata_code 双层 SSOT**：Java `MetaDataCodeEnum` enum 管平台编码；`sys_dict` 管 schema；租户可覆盖 dict 中的 `metadataCode` |

### 2.2 并发与写入

| # | 结论 |
|---|---|
| G5 | **`version INT` 乐观锁**；冲突返回 409 + 最新版 |
| G6 | 写 `content_json` 与 metadata 同步、revision 写入 **同一事务** |
| G7 | B 端：**整表 PUT**（全量 `contentJson` + `version`） |
| G8 | C 端：**独立 PATCH** `/me/archive/lifestyle`；服务端读全量 → merge 四块 lifestyle → save |

### 2.3 权限

| # | 结论 |
|---|---|
| G9 | C 端可改什么由 **接口分层** 控制，dict **不配** `editableBy` |
| G10 | C 端 P1 仅：饮食 / 运动 / 睡眠 / 生活习惯 |

### 2.4 修订历史

| # | 结论 |
|---|---|
| G11 | P1 必做；**通用能力**（注解 + AOP），后续 vitals 等可接入 |
| G12 | **头表 + 明细表**；`audit_log` 保留操作摘要 |
| G13 | Diff 粒度：**嵌套路径**（`diet.appetite`） |
| G14 | 修订值：原始 JSON + **display 快照**（可选列） |
| G15 | 注解挂在 **Service 方法**；校验 version → 读旧值 → 写库 → diff → revision |
| G16 | 病种归档：**P1 不做** |

### 2.5 迁移

| # | 结论 |
|---|---|
| G17 | 现有 `people_basic_archive` 无生产数据，**直接改 schema** |

## 3. 总体架构

```text
┌─────────────────────────────────────────────────────────────┐
│  编码层   MetaDataCodeEnum（Java enum，平台 metadata_code SSOT）   │
└──────────────────────────┬──────────────────────────────────┘
                           │ 种子注入 / 代码引用 / 检索条件
┌──────────────────────────▼──────────────────────────────────┐
│  配置层   sys_dict                                           │
│           OPTION / FIELD / DISEASE / DISEASE_FIELD           │
│           content: label, widget, metadataCode(可租户覆盖)    │
└──────────────────────────┬──────────────────────────────────┘
                           │ schema + options
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  文档层   people_basic_archive.content_json    （租户级）     │
│           people_disease_archive.content_json  （租户+病种）    │
└──────────────────────────┬──────────────────────────────────┘
                           │ MetadataSync（同事务）
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  索引层   people_metadata_info               （租户级）       │
└──────────────────────────┬──────────────────────────────────┘
                           │ 检索 / 规则 / AI
                           ▼
                    业务服务层

  修订：@RecordFieldRevision → field_revision_batch + field_revision_item
```

**读写分工：**

| 场景 | 数据源 |
|---|---|
| 表单渲染、详情、导出 | 档案 `content_json` + `sys_dict` |
| 列表筛选、统计、告警、Agent | `people_metadata_info` |
| 字段变更审计 | `field_revision_item` |
| 操作摘要 | `audit_log`（既有） |

## 4. 数据模型

> 约定对齐 `数据模型.md`：`pk_id` 物理自增；`id` VARCHAR(32) 雪花业务主键；软删四件套。

### 4.1 `sys_dict` — 系统字典

```sql
CREATE TABLE sys_dict (
    pk_id           BIGINT       NOT NULL AUTO_INCREMENT COMMENT '物理主键',
    dict_type       VARCHAR(32)  NOT NULL COMMENT 'OPTION/FIELD/DISEASE/DISEASE_FIELD',
    parent_code     VARCHAR(64)  NOT NULL DEFAULT '0' COMMENT '父级 code，0=顶级',
    dict_code       VARCHAR(64)  NOT NULL COMMENT '字典编码',
    dict_code_desc  VARCHAR(128) NOT NULL COMMENT '中文描述',
    content         JSON         NULL COMMENT '扩展配置（widget、metadataCode、optionRef 等）',
    sort_order      INT          NOT NULL DEFAULT 0 COMMENT '排序，越大越靠前',
    tenant_id       VARCHAR(32)  NOT NULL DEFAULT '0' COMMENT '0=平台通用，否则租户覆盖',
    is_deleted      TINYINT      NOT NULL DEFAULT 0,
    gmt_created     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    gmt_modified    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    gmt_deleted     DATETIME     NOT NULL DEFAULT '9999-12-31 23:59:59',
    PRIMARY KEY (pk_id),
    UNIQUE KEY uk_dict_tenant_type_parent_code (tenant_id, dict_type, parent_code, dict_code, gmt_deleted),
    KEY idx_dict_parent (tenant_id, dict_type, parent_code, sort_order)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='系统通用字典';
```

#### 4.1.1 `dict_type` 枚举

| dict_type | 用途 | parent_code 示例 |
|---|---|---|
| `OPTION` | 单选/多选选项 | `presentIllness`、`appetiteLevel` |
| `FIELD` | 基础档案字段定义 | `basic_archive` |
| `DISEASE` | 病种注册 | `0` |
| `DISEASE_FIELD` | 某病种下的字段定义 | `diabetes`、`hypertension` |

#### 4.1.2 字典合并

```text
effective = merge( platform(tenant_id='0'), tenant(tenant_id=真实租户) )
同 dict_type + dict_code → 租户记录优先
```

#### 4.1.3 FIELD content 示例

```json
{
  "metadataCode": "basic.presentIllness",
  "label": "现有疾病",
  "widget": "MULTI_SELECT",
  "required": false,
  "searchable": true,
  "optionRef": { "dictType": "OPTION", "parentCode": "presentIllness" }
}
```

```json
{
  "metadataCode": "basic.diet",
  "label": "饮食情况",
  "widget": "COMPOSITE",
  "fields": [
    { "code": "appetite", "label": "食欲", "widget": "SINGLE_SELECT",
      "optionRef": { "dictType": "OPTION", "parentCode": "appetiteLevel" } },
    { "code": "preference", "label": "饮食偏好", "widget": "TEXT" },
    { "code": "note", "label": "备注", "widget": "TEXT" }
  ]
}
```

COMPOSITE 默认 **FLAT** 拆 metadata，无需额外 `metadataStrategy` 字段。

### 4.2 `people_metadata_info` — 患者元数据

```sql
CREATE TABLE people_metadata_info (
    pk_id              BIGINT       NOT NULL AUTO_INCREMENT,
    id                 VARCHAR(32)  NOT NULL COMMENT '业务主键（雪花）',
    tenant_id          VARCHAR(32)  NOT NULL,
    people_id          VARCHAR(32)  NOT NULL,
    metadata_code      VARCHAR(100) NOT NULL COMMENT '如 basic.diet.appetite',
    metadata_value     JSON         NOT NULL COMMENT 'MetadataValue，见 §5.2',
    source_biz_code    VARCHAR(64)  NULL COMMENT 'BASIC_ARCHIVE / DISEASE_ARCHIVE',
    source_client_code VARCHAR(64)  NULL COMMENT 'B_WORKSPACE / C_APP / SYSTEM',
    is_deleted         TINYINT      NOT NULL DEFAULT 0,
    gmt_created        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    gmt_modified       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    gmt_deleted        DATETIME     NOT NULL DEFAULT '9999-12-31 23:59:59',
    PRIMARY KEY (pk_id),
    UNIQUE KEY uk_meta_people_code (people_id, metadata_code, gmt_deleted),
    KEY idx_meta_tenant_people (tenant_id, people_id),
    KEY idx_meta_tenant_code (tenant_id, metadata_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='患者元数据（租户级索引）';
```

**metadata_code 命名：**

```text
basic.{fieldCode}                      基础档案顶层或 FLAT 子字段
basic.diet.appetite                    复合字段子路径
disease.{diseaseCode}.{fieldCode}      病种档案
```

**双层 SSOT（v1.1）：**

| 层 | 职责 | 位置 |
|---|---|---|
| **MetaDataCodeEnum enum** | 平台标准 `metadata_code`；Java 查询/规则/Agent 引用 | `health-core/.../metadata/enums/MetaDataCodeEnum.java` |
| **sys_dict.content** | 表单 schema（label、widget、optionRef）；`metadataCode` 默认与 enum 一致，租户可覆盖 | DB + `DictFieldSchemas` 种子 |

新增平台字段时：**先加 enum 常量 → 再写 dict 种子 → 业务代码引用 enum**。

#### 4.1.4 MetaDataCodeEnum 平台注册表（P1）

| MetaDataCodeEnum | metadata_code |
|---|---|
| `BASIC_PRESENT_ILLNESS` | `basic.presentIllness` |
| `BASIC_FAMILY_HISTORY` | `basic.familyHistory` |
| `BASIC_PAST_HISTORY` | `basic.pastHistory` |
| `BASIC_DIET` / `BASIC_DIET_*` | `basic.diet` / `basic.diet.appetite` 等 |
| `BASIC_EXERCISE` / `BASIC_EXERCISE_*` | `basic.exercise.*` |
| `BASIC_SLEEP` / `BASIC_SLEEP_*` | `basic.sleep.*` |
| `BASIC_LIFESTYLE` / `BASIC_LIFESTYLE_*` | `basic.lifestyle.*` |
| `DISEASE_DIABETES_DIAGNOSIS_DATE` | `disease.diabetes.diagnosisDate` |
| `DISEASE_DIABETES_TYPE` | `disease.diabetes.diabetesType` |
| `DISEASE_DIABETES_TYPICAL_SYMPTOMS` | `disease.diabetes.typicalSymptoms` |
| `DISEASE_DIABETES_ATYPICAL_SYMPTOMS` | `disease.diabetes.atypicalSymptoms` |
| `DISEASE_HYPERTENSION_DIAGNOSIS_DATE` | `disease.hypertension.diagnosisDate` |

辅助方法：

```java
MetaDataCodeEnum.basicField("presentIllness")           // basic.presentIllness
MetaDataCodeEnum.basicCompositeSub("diet", "appetite")  // basic.diet.appetite
MetaDataCodeEnum.diseaseField("diabetes", "diagnosisDate")
```

#### 注解约定

```java
@RecordFieldRevision(bizType = "BASIC_ARCHIVE")
public BasicArchiveSaveResult save(SaveBasicArchiveCommand cmd) { ... }

@RecordFieldRevision(bizType = "DISEASE_ARCHIVE", bizKeySpel = "#cmd.diseaseCode")
public DiseaseArchiveSaveResult save(SaveDiseaseArchiveCommand cmd) { ... }
```

切面流程（**同一事务**）：

1. 校验请求 `version` 与 DB 一致，否则 409  
2. 读取旧 `content_json`  
3. 执行业务 UPDATE（`version + 1`）  
4. 嵌套 diff → 写 batch + items  
5. 调用 `MetadataSyncService.sync(...)`  
6. 写 `audit_log` 摘要（可选，与现有审计衔接）

### 6.1 MetadataSyncService 逻辑

```text
sync(tenantId, peopleId, bizCode, contentJson):
  schema ← DictService.listFields(tenantId, bizCode)
  existingCodes ← metadataRepo.listCodesByPrefix(...)

  for field in schema:
    metadataCode ← MetadataCodeResolver.resolve(
                     field.content.metadataCode,
                     codePrefix,           // basic. | disease.{code}.
                     field.dictCode)
    if field.widget == COMPOSITE:
      for sub in field.fields:
        path ← MetadataCodeResolver.compositeSub(metadataCode, sub.code)
        upsert(path, wrap(sub.widget, contentJson[field.code][sub.code]))
    else:
      upsert(metadataCode, wrap(field.widget, contentJson[field.code]))

  softDelete(existingCodes - newCodes)
```

**解析优先级：** `sys_dict.content.metadataCode` → 约定 `{codePrefix}{dictCode}`。若 dict 显式编码与平台 `MetaDataCodeEnum` 不一致，记录 debug 日志（允许租户扩展，检索侧需自行兼容）。

## 8. 保存流程

```text
Client → ArchiveService.save(cmd)
  ├─ RevisionAspect: 校验 version
  ├─ 读旧 content_json
  ├─ UPDATE archive SET content_json=?, version=version+1
  ├─ diff(old, new) → field_revision_batch + items
  ├─ MetadataSyncService.sync(...)
  └─ commit

C 端 PATCH → LifestyleArchiveService.merge(cmd)
  ├─ GET 完整 basic archive
  ├─ 覆盖 lifestyle 四字段
  └─ 委托 BasicArchiveService.save（同上）
```

## 9. 字段扩展约定

新增字段 **不改表结构**，流程：

1. `sys_dict` 插入 `FIELD` 或 `DISEASE_FIELD`（及所需 `OPTION`）  
2. 前端拉 schema 自动渲染  
3. 用户保存 → JSON 出现新 key  
4. `MetadataSyncService` 按 schema 自动 upsert metadata  
5. `FieldDiffUtils` 对新旧 JSON diff，revision 明细自动出现新 `field_path`
