## 1. 背景与目标

### 1.1 业务背景

Ops 开通租户并投放首管后，由 **租户管理员（TENANT_ADMIN）** 在 B 端完成机构与员工治理。  
核心模型：

| 维度 | 载体 | 含义 |
|---|---|---|
| **功能权限** | `staff_role_binding`（`org_id` 一律 NULL） | 菜单 / 按钮 / 业务操作 |
| **机构范围** | `staff_org_binding` | 账号可进入哪些机构 |
| **租户管理员特例** | 仅看角色 | **隐式拥有本租户全部机构**，不依赖 binding |

### 1.2 本期目标（In Scope）

| # | 能力 | 说明 |
|---|---|---|
| 1 | **机构管理** | 创建机构、列表；患者邀请码 |
| 2 | **账号管理** | 注册本租户 Staff、列表 |
| 3 | **角色分配** | 授予 `CARE_MANAGER` / `DOCTOR`（UI 单选；API 可多角色） |
| 4 | **机构权限** | `PUT /staff/{id}/orgs` 全量覆盖某账号的可访问机构 |

### 1.3 非目标（Out of Scope）

- 运营看板 / 履约分析（`TENANT_OPERATOR` **仅预留枚举**，业务完善后再做）
- 互授 / 撤销 `TENANT_ADMIN`；停用账号；角色撤销
- 员工邀请入职链接（P2；本期管理员直开账号）
- `ORG_ADMIN`（**废弃**，能力归租户管理员）
- Ops 跨租户治理

## 3. 角色与权限

### 3.1 B 端角色（均 `org_id = NULL`）

| 角色码 | 中文 | 本期 | 说明 |
|---|---|---|---|
| `TENANT_ADMIN` | 租户管理员 | ✅ 使用 | 建机构、账号、授角色、设机构权限；**机构范围=全租户** |
| `CARE_MANAGER` | 健管师 | ✅ 可分配 | 机构工作台；机构范围=binding |
| `DOCTOR` | 医生 | ✅ 可分配 | 同上 |
| `TENANT_OPERATOR` | 运营 | 预留 | 用户/履约数据分析；**本期不分配、无菜单** |
| `ORG_ADMIN` | — | **废弃** | 不再分配；邀请码改由管理员 + 一线角色（见下） |

约束：

- 不可通过 B 端再授 `TENANT_ADMIN`（仅 Ops）。
- API 支持一人多角色；**UI 本期单选**一个功能角色。
- 权限取角色并集；数据范围取「TENANT_ADMIN 全量」或「binding 列表」。

### 3.2 邀请码谁可发（Q21）

| 角色 | 范围 |
|---|---|
| `TENANT_ADMIN` | 本租户任意机构 |
| `CARE_MANAGER` / `DOCTOR` | 仅其 `staff_org_binding` 内机构 |

### 3.3 鉴权摘要

```text
requireTenantAdmin()     → 账号/角色/机构权限写操作、建机构
canAccessOrg(staff, org) → TENANT_ADMIN ? true : hasBinding(staff, org)
requireCurrentOrgId()    → 工作台业务；无 binding 且非管理员切机构 → 提示未分配机构
```

## 4. API 设计

统一前缀：`/api/b/v1`，租户取自 JWT（禁止 body/path 覆盖）。

### 4.1 机构（已有 + 行为澄清）

| 方法 | 路径 | 权限 |
|---|---|---|
| POST | `/orgs` | TENANT_ADMIN；**不**自动写 binding |
| GET | `/orgs` | 登录员工；管理员看全部，其他看 binding |
| POST | `/orgs/{orgId}/invites` | 见 §3.2 |

### 4.2 注册账号

`POST /staff-accounts`（TENANT_ADMIN）

```json
{
  "username": "acme_cm01",
  "password": "ChangeMe123!",
  "displayName": "李四",
  "mobile": "13900000000",
  "title": "健管师",
  "roleCode": "CARE_MANAGER",
  "orgIds": [10, 11]
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| username / password / displayName | 是 | username 全局唯一 |
| roleCode | 否 | UI 单选；禁止 `TENANT_ADMIN` / `TENANT_OPERATOR`（本期） |
| orgIds | 否 | 初始机构权限；写 `staff_org_binding` |

### 4.3 账号列表

`GET /staff-accounts`  
Query：`keyword`、`status`、`roleCode`、`orgId`、`page`、`pageSize`  
仅本 `tenant_id`。

### 4.4 授予功能角色

`PUT /staff/{staffId}/roles`（TENANT_ADMIN）

```json
{ "roleCodes": ["CARE_MANAGER"] }
```

- 本期 UI 传单元素数组；禁止含 `TENANT_ADMIN`。
- **全量替换**该员工除系统保留外的功能角色（或：只允许 CARE_MANAGER/DOCTOR 集合内 replace）。
- **不**改动 `staff_org_binding`。
- 幂等。

> 简化实现可选：`PUT` 仅设置唯一 `roleCode` 字符串，与 UI 单选对齐；多角色留字段扩展。

**建议本期实现**：`{ "roleCode": "CARE_MANAGER" | "DOCTOR" | null }` 单角色替换。

### 4.5 机构权限全量覆盖

`PUT /staff/{staffId}/orgs`（TENANT_ADMIN）

```json
{ "orgIds": [10, 11, 12] }
```

- 覆盖该员工全部 binding；空数组=清空机构权限。
- 所有 `orgId` 必须属于本租户。
- 不自动改角色。
- 审计：`STAFF_ORG_BIND_REPLACE`。

### 4.6 查询某人角色与机构（可选）

`GET /staff/{staffId}` → profile + roles + orgIds

## 5. 服务层

```text
TenantAdminService
  createOrg / listOrgs（可委托 OrganizationService）
  registerStaff
  listStaff
  replaceStaffRole
  replaceStaffOrgs
```

事务：`registerStaff` = account+profile[+role][+bindings]；`replaceStaffOrgs` = 删旧+插新。

复用 Ops 列表 SQL 思路，`tenantId` 固定来自 JWT。

## 7. 前端（`/tenant`）

```text
/tenant/orgs     机构 + 邀请码
/tenant/staff    账号列表 / 注册 / 设角色 / 设机构权限
```

- 不做 `/tenant/ops`（运营后期再做）。
- 角色下拉：健管师、医生（中文）。
- 机构权限：多选本租户机构，提交全量 `orgIds`。
- 菜单：机构管理、账号与权限。

---

## 8. 典型流程

```text
Ops 快捷开通 → TENANT_ADMIN 登录
  → POST /orgs 建机构（不强制绑自己）
  → POST /staff-accounts（角色=健管师 + orgIds）
  → 或分步：注册后再 PUT roles / PUT orgs
  → 员工登录工作台，凭 binding 选 currentOrgId
```
