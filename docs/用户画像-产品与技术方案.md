### 命名边界

| 概念 | 说明 |
|------|------|
| **用户画像** | 本方案：面向健管师的**单患者案头画像**（谁 / 卡在哪 / 盯什么）；UI 副文案「健管案头摘要，非病历」 |

| 点 | v0.1 | v0.2 |

## 1. 产品定位

### 1.1 一句话

把分散的首诊、评估、档案、方案、依从、待办收成一张案头卡：**这个人是谁、现在卡在哪、下一步盯什么**——先服务健管师案头人审，再（P2）喂给 Agent / 驾驶舱。

### 1.2 解决什么问题

| 现状 | 痛点 |
|------|------|
| 患者详情 Tab 多、信息散 | 交接 / 开班要翻多页才能拼出「这个人」 |
| 首诊 `aiSummary` 只停在提交时点 | 方案上线、依从变差、评估升级后案头不演进 |
| 评估标签 + 依从卡各自独立 | 缺「人设叙事」与「盯梢点」串联 |
| 方案 Agent 上下文大而碎 | 缺稳定、短、可人审的 `personaBrief`（P2） |

### 1.3 成功标准（P1 实现后）

1. 进入患者详情，**首屏紧凑条**可见：headline（或规则灰字）+ 盯梢/下一步 + 生成·刷新·展开  
2. 「生成叙事」走 LLM，失败落模板；「刷新」持久化重算维度，未锁则重写叙事  
3. 人工编辑叙事后整包锁定；解锁后方可被覆盖  
4. C 端任何页面**不出现**画像  
5. （P2）`CarePlanContext` / 驾驶舱可读 `personaBrief`

### 1.4 角色

| 角色 | 用法 |
|------|------|
| 健管师 | 速览、生成、刷新、编辑并锁定 |
| 租户管理员 | 同健管师（写） |
| 同机构医生 | **只读** |
| 患者（C） | **不可见** |

## 2. 信息架构与入口

### 2.1 患者详情（P1 主入口）

```text
患者详情
  ├─ hero（姓名 / 首诊 / 评估·病情标签 / 依从轻卡）  ← 保留
  ├─ 【用户画像】紧凑条（默认；副文案：健管案头摘要，非病历）
  │     headline 或规则灰字
  │     watchPoints（有叙事）或 focus.nextStep（无叙事）
  │     [生成叙事] [刷新] [编辑] [展开]
  ├─ 展开区（默认收起）
  │     六维只读明细 + 全文 narrative
  └─ 既有 Tabs
```

- **不**新增侧栏菜单；不抢驾驶舱主对话。  
- hero 评估/依从**不删**；紧凑条不重复堆风险芯片。  
- 手机工作台：P1 不做；P2 患者详情只读缩略。

### 2.2 驾驶舱与 Agent（P2）

选中患者：焦点条 `headline` + 最多 2 条 `watchPoints` → 点进详情画像。  
开场简报 / 方案 Context 带入 `personaBrief`（与案头同源、已经人审或模板）。

### 2.3 数据流

```text
源数据（首诊·评估·档案·方案打卡·用药·OPEN 待办）
        │
        ▼
  GET：aggregateDimensions（规则）──► 响应 dimensions（不写库）
        │
        │  generate / refresh / 首诊钩子 / P2 事件
        ▼
  upsert people_persona.dimensions_json
        │
        ▼（若需叙事且未整包锁）
  PersonaLlmGenerator → 失败则模板落库
        │
        ▼
  narrative_json（staffLocked 整包）
        │
        ▼ P2
  personaBrief → CarePlanContext / 驾驶舱
```

## 3. 结构化维度

规则聚合，**不调 LLM**。缺数据用 `null` / `[]`，UI 显示「未采集 / 暂无」。

### 3.1 六块（P1 全留）

| key | 名称 | 主要数据源 | 展示要点 |
|-----|------|------------|----------|
| `identity` | 管理身份 | profile、membership、assignment、care_team、方案类型/tags | 年龄性别、主管、健管组、入组天数、方案类型 |
| `goals` | 目标与诉求 | goals、首诊 keyAnswers / highlights | 主诉求、careTracks、目标体重等 |
| `risk` | 风险与病情 | `people_assessment_latest`、病种档案 | 患病风险 / 严重分层 / 疑似患病 |
| `constraints` | 约束与禁忌 | 过敏、用药、首诊 highlights | 过敏原、运动限制、孕哺等 |
| `execution` | 执行画像 | 方案打卡、用药依从、激励火苗 | 近 7 日完成率、连续未完成、`flameStatus`（无则 null） |
| `focus` | 当前焦点 | OPEN 任务、依从红灯、评估升级 | ≤5 条待办 + 规则 `nextStep`（非 LLM） |

`execution` 口径与**依从性看板同一套**。

### 3.2 `nextStep` vs `watchPoints`

| 字段 | 来源 | 用途 |
|------|------|------|
| `dimensions.focus.nextStep` | 规则模板 | 无叙事时紧凑条「下一步」；`personaBrief.nextStep` 回落 |
| `narrative.watchPoints` | LLM（或失败模板从 openTasks/过敏截取） | 有叙事时紧凑条优先展示（≤3） |

### 3.3 `dimensions_json` 示意

```json
{
  "identity": {
    "age": 52,
    "sex": "FEMALE",
    "primaryCareManagerName": "李健管",
    "careTeamName": "代谢组",
    "enrolledDays": 86,
    "activePlanTemplateKey": "DIABETES",
    "diseaseTags": ["DIABETES"]
  },
  "goals": {
    "summary": "控糖并减重 5kg",
    "careTracks": ["GLUCOSE", "WEIGHT"],
    "fromIntake": true
  },
  "risk": {
    "tags": [
      { "diseaseCode": "DIABETES", "category": "SEVERITY", "level": "HIGH", "levelLabel": "高危" }
    ]
  },
  "constraints": {
    "allergens": ["青霉素"],
    "highlightCodes": ["EXERCISE_LIMIT"],
    "notes": ["膝关节不适，避免冲击跑"]
  },
  "execution": {
    "planCompletion7d": 0.57,
    "medCompletion7d": 0.86,
    "planMissStreak": 3,
    "medMissStreak": 0,
    "flameStatus": "BROKEN"
  },
  "focus": {
    "openTasks": [
      { "type": "PLAN_NUDGE", "title": "连续 3 日方案未完成" }
    ],
    "nextStep": "先电话确认未打卡原因，再决定是否调整运动强度"
  },
  "aggregatedAt": "2026-11-01T08:00:00+08:00",
  "sourceFingerprint": "sha256:…"
}
```

`sourceFingerprint`：关键源版本/更新时间拼串哈希。用于 **P2 事件**判断「相对上次叙事生成是否值得重写」；P1 首诊提交**不**靠 fingerprint 省略叙事（未锁则写）。

## 4. AI 叙事

### 4.1 `narrative_json`

```json
{
  "headline": "控糖减重期 · 执行偏弱的中年女性患者",
  "narrative": "……120–220 字……",
  "watchPoints": [
    "近 3 日方案打卡连续缺口",
    "糖尿病分层高危，注意低血糖症状沟通",
    "青霉素过敏，开方/宣教勿遗漏"
  ],
  "model": "…",
  "generatedAt": "…",
  "staffLocked": false,
  "editedByStaffId": null,
  "editedAt": null
}
```

约束：

- `headline` ≤ 40 字；`narrative` 120–220 字；`watchPoints` 1–3 条，每条 ≤ 28 字  
- 缺数据须写明「尚未完成首诊 / 暂无评估」等，**禁止编造**  
- B 端可用高危/分层（对齐 R18 / D17）  
- **禁止**对患者口吻、处方剂量、无依据的确诊断言  
- `staffLocked`：**整包** boolean（非分字段）

### 4.2 触发

| 触发 | 行为 | 分期 |
|------|------|------|
| GET 患者画像 | 聚合维度进响应；**不写库**；不调 LLM；无叙事时附带规则灰字 headline（仅响应、不落库） | P1 |
| 首诊 / 待补 SUBMITTED | 异步：upsert 维度；若 `!staffLocked` 则生成/覆盖叙事（失败→模板） | P1 |
| 「生成叙事」 | upsert 维度 + LLM 叙事；已 GENERATING → **409**；失败模板落库、`staffLocked=false` | P1 |
| 「刷新」 | 持久化重算维度；若未锁则重写叙事；已锁则**仅维度**并提示已锁 | P1 |
| 「编辑保存」 | PUT 叙事，`staffLocked=true` | P1 |
| 「解锁」/「解锁并刷新」 | `staffLocked=false`；可选立即 refresh 叙事 | P1 |
| 方案发布 / 评估升级 / 报告发布 | upsert 维度；仅当未锁 **且** fingerprint 相对上次叙事已变 → 异步重写叙事 | P2 |
| 定时批跑 | **不做** | — |

### 4.3 无叙事时紧凑条

- headline 位：规则拼接灰字（与 §4.4 模板同行算法），**不落库**  
- 主按钮：「生成叙事」  
- 次要信息：`focus.nextStep`（可空）

### 4.4 LLM 失败降级

模板：`{方案类型或「未建方案」} · {最高风险标签或「暂无评估」} · {执行：近7日完成率或「暂无打卡」}`  
`watchPoints` 从 `openTasks` 与 `allergens` 截取。  
**落库**，`model: "template"`，`staffLocked: false`；UI 提示「模板摘要，可再生成」。

### 4.5 P1 Prompt 上下文

dimensions 全量 + 首诊 `aiSummary`（截断）+ 评估标签 + 过敏 + 近 7 日依从数字。  
**不塞**：检验原文、聊天全量、**管理报告要点**（报告进 prompt 留 P2）。

## 5. 与既有模块边界

| 模块 | 关系 |
|------|------|
| 首诊 `intakeBrief` / `staff.aiSummary` | 输入；提交钩子触发生成；不回写 answers |
| `people_assessment_latest` | 输入；不触发重算 |
| 病种 / 基础档案 | 输入；过敏与确诊 tags 以档案为准 |
| `CarePlanContextService` | P2 增加 `personaBrief`；聚合逻辑可复用 |
| 依从性看板 | `execution` 同口径 |
| 管理报告 | P1 不进 prompt；P2 可引最近 PUBLISHED 要点 |
| 驾驶舱 | P2 消费 brief；不在舱内编辑长文 |
| C 端激励 / 火苗 | `flameStatus` 只读；无则 null |

**禁止**：画像写方案/评估、自动办结、自动发报告。

## 6. 数据模型

### 6.1 `people_persona`

| 列 | 说明 |
|----|------|
| `id` | 业务主键 |
| `tenant_id` / `people_id` | `UK(tenant_id, people_id)` |
| `dimensions_json` | §3；仅在 generate/refresh/首诊/P2 事件等写路径更新 |
| `narrative_json` | §4；可空（仅有过写路径后才有） |
| `source_fingerprint` | 与最近一次**持久化**维度一致 |
| `narrative_fingerprint` | 生成该版叙事时所基于的 fingerprint（供 P2 门闸） |
| `status` | `READY` / `GENERATING` / `FAILED`（无行时靠 GET 的 `persisted=false`，不单造 EMPTY 行） |
| `generated_at` | 最近叙事写入（含模板） |
| `dimensions_at` | 最近**持久化**维度时间 |
| `edited_by_staff_id` | 最近人工编辑者 |
| `created_at` / `updated_at` | 常规 |

双主键与租户隔离见 `数据模型.md`。

### 6.2 审计

简单操作日志（或现有审计扩展）：`generate` / `refresh` / `edit` / `unlock`（谁、何时、peopleId）。**不**走患者病历 revision 流。

### 6.3 不改动的表

首诊 answers、评估、方案、打卡等不为画像加列。

## 7. API（B 端）

权限：与患者详情可见范围一致；**写**限健管师与租户管理员（医生 403）。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/b/v1/patients/{peopleId}/persona` | 始终 **200**：新鲜 `dimensions`；库存 `narrative` 可空；`persisted`；`status` |
| POST | `/api/b/v1/patients/{peopleId}/persona/generate` | 持久化维度 + 生成叙事；`GENERATING` 时 **409** |
| POST | `/api/b/v1/patients/{peopleId}/persona/refresh` | 持久化维度；未锁则重写叙事；已锁仅维度 |
| PUT | `/api/b/v1/patients/{peopleId}/persona/narrative` | 保存人工叙事，`staffLocked=true` |
| POST | `/api/b/v1/patients/{peopleId}/persona/unlock` | 清锁；`?refresh=true` 则解锁后重写叙事 |

**无 C 端 API。**

### 7.1 GET 响应

```json
{
  "peopleId": "…",
  "persisted": false,
  "status": null,
  "dimensions": { },
  "narrative": null,
  "displayHeadline": "未建方案 · 暂无评估 · 暂无打卡",
  "sourceFingerprint": "sha256:…",
  "generatedAt": null,
  "dimensionsAt": null
}
```

- `displayHeadline`：有叙事用 `narrative.headline`；否则规则灰字（与紧凑条一致）。  
- `persisted=true` 时带库内 `status` / `dimensionsAt` / 可能非空的 `narrative`。  
- 响应中的 `dimensions` **总是**本次聚合结果（即使 `persisted` 且库内维度较旧）。

### 7.2 `personaBrief`（P2）

```json
{
  "headline": "…",
  "watchPoints": ["…"],
  "nextStep": "…",
  "staffLocked": false,
  "model": "…",
  "generatedAt": "…"
}
```

`nextStep`：优先不占用；消费方展示顺序与紧凑条相同（watchPoints 优先，否则 dimensions.focus.nextStep）。无叙事且无持久化时 brief 可空，Agent 降级不依赖画像。
