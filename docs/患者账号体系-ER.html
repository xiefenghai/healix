Healix · Target Architecture

患者账号体系 · 重构目标模型

核心原则：C 端没有租户。C 端是互联网账号；自然人 people_id 平台唯一；租户/机构只出现在 B 端「在管关系」上。 C 与 B 通过同一条 people_id 对齐；对齐键是手机号 + 姓名， C 端添加就诊人额外要求短信 OTP。证件仅作可选档案字段，不参与对齐。

C 账号全局唯一 people_id 平台级 租户只在 B 在管关系 对齐：手机号 + 姓名 加就诊人需 OTP

1. 三层拆开：别再把租户塞进 C

以前失败点是把「登录账号」和「机构在管」揉进同一租户边界。重构后三者职责分离。

层 1 · C 登录身份

people_account
  • 无 tenant_id
  • 手机号（username）全平台唯一
  • 只负责登录 / 会话 / 家庭管理权
  • 一个账号可挂多个就诊人

层 2 · 核心 自然人

people_profile
  • people_id B/C 共用主键
  • 无租户归属（平台级自然人）
  • 对齐键：手机号 + 姓名
  • 证件可选、不参与对齐
  • 可被 C 创建，也可被 B 创建

层 3 · B 在管关系

membership / care
  • people_org_membership：机构是否在管
  • people_care_assignment：主管健管师
  • 租户只存在于机构 / 员工侧
  • B 建档 ≠ 新建自然人（可复用已有 people）

2. 一眼看清：谁连谁

中间是自然人；左边是 B 的在管边；右边是 C 的家庭卡片边。

B 健管端 机构在管关系
membership + 健管师
⟷
自然人 people_profile people_id · 平台唯一
⟷
C 患者端 账号 + 就诊人卡片
account → account_patient

3. 三条业务路径

按「有没有健管师」和「谁先创建自然人」拆开。最终都收敛到同一个 people_id。

路径 A

自然流量 · 无健管师

C 注册账号people_account（全局）
→
添加就诊人填手机号 + 姓名
→
短信验证码验证该手机号归属
→
写就诊人卡片新建 people + account_patient
→
自用服务无 membership · B 不可见

说明：此时只有 C 账号 + 家庭就诊人。没有机构在管，也就没有租户上下文。

路径 B

C 先建档 → 健管端再接入

C 已有账号 + 就诊人people_id 已存在
→
B 建档查重手机号 + 姓名
→
命中已有 people不新建档案
→
写机构关系membership + 健管师
→
C 自动可见在管同一 people_id

关键：B「建档」变成「建立机构—自然人关系」，而不是再造一份租户内档案。

路径 C

健管端先建档 → 用户后注册

B 建档新建 people + membership
→
患者尚未有 C 账号可无 account_patient
→
用户注册 / 登录全局 people_account
→
添加就诊人手机号+姓名查重 + OTP
→
命中则复用account_patient → 同一 people_id

关键：C 添加就诊人 = 平台级查重 + 对该手机号发 OTP；OTP 通过才允许绑定/新建，命中则复用，绝不静默造第二份。

4. 目标 ER（可读版）

绿色=平台级核心；蓝色=仅 B 侧租户边界。C 账号与自然人不再挂 tenant。

5. 跨端对齐规则

证件敏感、弱化处理。对齐只靠「手机号 + 姓名」；C 端加就诊人必须再过一道短信 OTP，证明号在手上。

对齐键：手机号 + 姓名

  • B 建档 / C 添加就诊人：按 手机号 + 姓名 平台查重
  • 全匹配 → 复用已有 people_id
  • 同号但姓名不同 → 视为不同人（家庭共用号场景），各自一份 people
  • 同号同名已存在 → 禁止再新建，走复用 / 绑定

C 加就诊人：强制 OTP

  • 向该就诊人填写的手机号发送验证码
  • OTP 通过后才允许：查重命中则绑卡片，未命中则新建 people
  • 本人（登录号 = 就诊人号）也可再验一次，规则统一、少特例
  • OTP 失败 / 过期 → 不写库

证件：可选、不参与对齐

  • people_identity 可保留作档案补充，默认不采集
  • 不用证件哈希做查重 / 合并 / 绑定判定
  • B 端如需填写证件，仅展示与存储，不影响 people_id 归属

绑定 / 在管判定

  • C 已绑定：只认 account_patient；废弃 people.account_id
  • B 在管：membership.status = ACTIVE
  • B「C 已上线」：该 people 至少一张卡片

6. 创建 / 绑定自然人时的决策流

B 建档只做手机号+姓名查重；C 加就诊人在查重前后都必须过 OTP。

7. 相对现状：改什么

对照当前线上模型（租户内账号 / bootstrap 默认租户）的关键差异。

现状（问题源）

  • people_account(tenant_id, username) 唯一 → 同号多账号
  • people_profile 租户隔离 → 同一人可有多份档案
  • C 登录依赖 /auth/bootstrap 默认租户
  • 跨端对齐依赖激活码「定租户」
  • people.account_id 与卡片双轨，易误判

目标（本页）

  • people_account.username 全局唯一，无租户
  • people_profile 平台级，一人一份
  • C JWT 只有 account + 当前 people，不带租户
  • 跨端对齐：手机号 + 姓名；C 加就诊人强制 OTP
  • 证件弱化：可选存储，不参与对齐
  • 只认 account_patient；废弃 account_id 判定
