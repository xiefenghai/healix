0. 摘要

Healix 是面向医疗机构的多租户健管 SaaS：

  • 三角色：C 患者 / B 健管（含租户管理）/ Ops 平台，分入口、分 JWT aud。
  • 后端形态：Spring Boot Modulith 单体（health-app 统一暴露 API），领域与智能体分模块。
  • B 端主入口：智能驾驶舱（对话驱动）+ 传统菜单底座。
  • AI 原则：起草与预填；人确认后才写业务库（方案 publish、OCR 确认入库、任务/随访提交）。
多租户 SaaS
 ├── C    aud=c     frontend-user
 ├── B    aud=b     frontend-admin
 └── Ops  aud=ops   （同壳分菜单）
          │
          ▼
 Spring Boot 3.3 / Java 21 · health-app
 ├── health-common   JWT · 证件加密 · 工具
 ├── health-core     档案·任务·随访·方案·观测…
 └── health-agent    CARE_COPILOT · Skill · SSE
          │
          ▼
 MySQL · Redis · DeepSeek（Spring AI）

1. 整体架构设计

1.0 架构总览

自上而下：三角色客户端 → 分 aud 的统一 API → Modulith 单体（app / agent / core / common）→ 数据与模型基础设施。

1.1 设计目标

#目标落地方式
1多租户可运营行级 tenant_id + 机构工作上下文
2账号与权限隔离C/B/Ops 三套账号 + JWT aud
3业务可演进Modulith 模块边界，先单体后按需拆
4AI 可追责模型不直写业务表；动作卡调现有 B API
5对话即工作台驾驶舱 SSE + Skill 路由 + 动作卡

1.2 仓库与模块

路径职责
backend/health-common通用模型、EntityMeta、JWT、身份证加解密、IdCardUtil
backend/health-core领域核心：租户/机构/员工、档案、观测、方案、任务、随访、报告、沟通、驾驶舱…
backend/health-agent智能体：Gateway、Skill、LLM、OCR、会话记忆、SSE
backend/health-appBoot 启动、Controller、Schema 保障、安全过滤器
frontend-adminB + Ops 同壳（Vue）
frontend-userC 端 H5

技术栈： Java 21 · Spring Boot 3.3 · MyBatis · JWT · Spring AI / DeepSeek · Redis · Vue 管理端。

1.4 多租户与机构模型

概念含义
租户 tenantSaaS 客户边界；患者 people 归属单租户
机构 organizationB 端工作边界；员工切换 currentOrgId
健管组 care_team机构内网格；成员含 STAFF / PATIENT
入组 membershippeople_org_membership；ACTIVE 才在机构患者列表可见

隔离约定

数据类型隔离
体征 / 检验 / 检查报告租户共享（同租户机构可见历史）
工作台任务 / 随访记录机构隔离（org_id）
Agent 会话（B 健管）租户 + 员工 +（可选）患者 / 机构会话
C 端患者私聊与 CARE_COPILOT 记忆隔离（双 Agent）

1.5 认证与 API 分区

入口前缀Token
C/api/c/v1/**aud=c
B/api/b/v1/**aud=b，带 tenantId / staffId / currentOrgId
Ops/api/ops/v1/**aud=ops
公开/api/public/v1/**极少

管理端登录三分入口：平台超管 / 租户管理 / 机构工作台——菜单与 aud、角色绑定，互不串用。

1.6 B 端主链路：智能驾驶舱

今日优先（CockpitService）
    → 选患者 focus（档案完整度 / 依从 / OPEN 任务 / 待确认草稿）
    → POST /api/b/v1/agent/chat/stream  （SSE）
    → StaffAgentGateway 路由 Capability
    → Skill 执行（可带 LLM / OCR / 工具）
    → 回复 + AgentAction[] 落会话
    → 前端动作卡 → 现有 B API 或 WorkspaceTaskFormDialog
    → 人确认 → 业务表
会话peopleId能力约束
机构会话空强制偏 GENERAL_CHAT；引导点人；不可直接方案/OCR 写库路径
患者会话有可方案 / OCR / 办结 / 报告点评

1.7 前端结构（B）

  • 布局：WorkspaceLayout 侧栏（驾驶舱、工作台、患者管理、沟通、依从、报告、运营统计…）
  • 驾驶舱：CockpitView 三栏 + Sheet 抽屉复用患者详情
  • 代理：Vite 将 /api 转到后端 8080

1.8 为何 Modulith 不先拆微服务

  • 用模块表达边界（core / agent / app），降低运维成本
  • Agent 强依赖领域服务与同一事务边界（办结、确认入库）
  • 边界清晰后再按调用热点拆（例如 OCR/LLM 异步 worker）

2. 数据库设计

2.1 通用约定

约定说明
库MySQL 8.0 / utf8mb4
双主键pk_id BIGINT 自增；id VARCHAR(32) 雪花业务主键（UK）
外联tenant_id / org_id / people_id 等指向对方 id
软删is_deleted + gmt_deleted（未删默认 9999-12-31 23:59:59）
时间gmt_created / gmt_modified；业务时刻 DATETIME
写入EntityMeta.onCreate / onUpdate / onSoftDelete
Schema主 DDL + SchemaEnsureRunner 启动保障

（5）工作台任务与随访

workspace_task

  • task_type：FOLLOW_UP / METRIC_ALERT / PLAN_NUDGE / …
  • biz_key + 生成列 open_dedup_key
  • OPEN 去重：同租户机构不重复
  • assignee 空=公共池；有值=个人池

followup_record

  • record_type：PERIODIC / METRIC_REVIEW / PLAN_NUDGE
  • OPEN（草稿）/ DONE / CANCELLED
  • 关联 workspace_task_id
  • content_json 填单内容
创建/排期 → OPEN 任务 ↔ OPEN 随访
   ├─ 填单「保存」→ 更新 content_json，状态仍 OPEN
   ├─ 填单「提交」→ 随访 DONE + 任务 DONE
   └─ 当场办结 → DONE，并关闭同人同 followupType 的 OPEN FOLLOW_UP

（6）报告 / 沟通 / 通知 / 评估

表说明

care_chat_thread / messageB↔C 沟通
notify_message / delivery站内提醒投递
people_assessment_snapshot评估标签快照
adherence_daily_snapshot依从日快照

（7）Agent 与审计

表说明

（8）基础设施作业

sys_job_def / sys_job_run — 随访排期、依从扫描等。

2.4 索引与去重要点

  • 工作台 OPEN：uk_workspace_task_open (tenant_id, org_id, open_dedup_key, gmt_deleted)
  • 任务查询：org + status + assignee / people；opened_at / done_at
  • 证件：租户内 identity_type + hash 唯一
  • 患者列表：ACTIVE membership，按 COALESCE(joined_at, gmt_created) DESC

2.5 敏感数据

数据策略
身份证号规范化校验 → 哈希查询 + AES 密文 + 脱敏展示
OCR 原图请求内短暂使用；不落业务表、不进模型日志正文
Ops 明文检索走审计（如 OPS_PHI_VIEW）

3. Agent 架构与技术实现

3.1 定位

项口径
Agent 名B 端 CARE_COPILOT（灵犀 / 健管智能体）
入口驾驶舱对话、（历史）侧栏 Agent Drawer
非目标替代诊疗；自动写业务库；机构会话无患者上下文出方案落库

C 端 PATIENT Agent 与 CARE_COPILOT 会话记忆隔离（agent_type 区分）。

3.2 包结构（health-agent）

com.healix.agent
├── gateway/          StaffAgentGateway · AgentCapability · AgentAction
├── skill/            GeneralChat / CarePlan / ReportSummary / Ocr*
├── stream/           AgentStreamEvent（SSE）
├── memory/           Session / Message · ConversationService · SessionStore
├── llm/              LlmClient · DeepSeekChatCompletionsClient
├── careplan/         CarePlanAgentService · 流式生成
├── ocr/              Lab/Exam/Med 识别 · Vision · Ingest
├── cockpit/          CockpitBriefingService
├── tool/             StaffBizTools
├── safety/           安全链（可扩展）
└── config/           AgentLlmConfig · ModuleConfig

3.3 请求链路（SSE）

HTTP： POST /api/b/v1/agent/chat/stream → TEXT_EVENT_STREAM

BAgentController
  → 组装 AgentChatCommand
  → StaffAgentGateway.streamChat(cmd, sink)
       1. ensureSession + 加载 history
       2. route(capabilityHint / 话术 / 是否带图)
       3. 机构会话：非 GENERAL_CHAT 降级为 GENERAL_CHAT
       4. 执行对应 Skill（流式或同步）
       5. 有有效 reply 才成对落库（防半截气泡）
       6. emit result + done
  → AgentSseSupport 写 SSE

典型事件：skill progress thinking* tool token result done

3.4 Capability 路由

CapabilitySkill说明
GENERAL_CHATGeneralChatSkill建议、办结引导、机构简报；可附 AgentAction
CARE_PLANCarePlanSkill方案草稿流式生成
REPORT_SUMMARYReportSummarySkill管理报告点评草稿
OCR_LAB / EXAM / MEDOcr*Skill识别结构化预填
（自动）带图 + GENERAL_CHAT + 有患者OCR 自动分类先分类再进 LAB/EXAM/MED

前端芯片：今日建议 / 生成方案 / 报告点评 / 单据录入 / 完成待办。

3.5 动作卡（AgentAction）

动作是确定性协议，不依赖模型编造 path：

type含义前端行为
FOCUS_PATIENT点人selectPatient
OPEN_SHEET打开抽屉archive / care-plan / followups…
CALL_API调 B APINUDGE / COMPLETE_TASK / PUBLISH_*…
TRIGGER_CAPABILITY再发一轮带 capabilityHint
REFRESH / NAVIGATE刷新或跳转—

办结： COMPLETE_TASK → 与工作台同一 WorkspaceTaskFormDialog；公共池未领则静默 claim。去重含 payload.taskId。

3.6 Skill 与 LLM · 人在环

能力LLM失败策略
GENERAL_CHATDeepSeek 流式（可关）模板/降级文案
CARE_PLAN要求 LLM失败显式报错
OCRVision / TEXT_LLM识别失败提示；不落库
REPORT_SUMMARYLLM草稿级，发布另接口
产出持久化时机
对话回复 / actions会话表（非业务主数据）
方案结构draft/version；publish 生效
OCR extracted前端预填；确认入库 写业务表
任务填单保存=OPEN 草稿；提交=DONE+关任务

3.7 会话记忆

  • AgentConversationService.ensureSession：按员工 + 机构/患者会话复用或创建
  • StaffSessionStore：最近轮次供 LLM history
  • 仅当助手有有效内容才落成对消息，避免刷新后「用户气泡墙」

3.8 与领域服务的边界

health-agent                          health-core
────────────                          ───────────
读：CockpitService.focus / topUrgent  权威业务写入
读：档案/方案上下文摘要               WorkspaceTaskService.submitForm / saveFormDraft
写：仅 agent_session/message/log      FollowupService.complete / createPeriodic
                                      CarePlan publish
                                      Lab/Exam/Med 确认入库

原则： Agent 不直接 UPDATE 业务主表；通过动作卡或确认 API 进入 core。

3.9 安全与配额

  • safety 责任链：过敏、运动-血糖等（可插拔）
  • AiUsageGuard：用量护栏位
  • 启动日志打印 llm/vision 是否配置，便于演示排查

4. 关键业务闭环

方案

CARE_PLAN

芯片生成 → SSE → draft/version → 审阅 → publish → ACTIVE

OCR

单据识别

上传图 → Skill 预填卡 → 人改 → 确认入库 → lab/exam/med

任务与随访

双入口闭环

排期/手动 → OPEN 任务↔随访 → 驾驶舱办结 / 工作台处理 / 详情当场办结 → 保存草稿或提交 DONE
